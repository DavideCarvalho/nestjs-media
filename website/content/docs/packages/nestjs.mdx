`@dudousxd/nestjs-media` is the package you import in a Nest app. It wires [core](/docs/packages/core) into NestJS DI and exposes everything through one service.

## `MediaModule`

`forRoot` / `forRootAsync` register a `@Global()` module. It always provides the storage layer; pass `store` for the media-library, `uploadSessions` for resumable uploads, `tus` to mount the proxy HTTP controller, and `direct` to mount the direct presigned-multipart controller. See [Reference → Configuration](/docs/reference/configuration) for every option.

```ts
MediaModule.forRoot({
  default: 'local',
  disks: { local },
  store,                  // → media.library
  uploadSessions,         // → media.uploads
  tus: { disk: 'local' }, // → mounts MediaUploadController
  direct: { disk: 's3' }, // → mounts MediaDirectUploadController (S3)
});
```

## `MediaService`

The single injectable surface:

```ts
class MediaService {
  disk(name?: string): StorageDriver;        // layer 1
  get library(): MediaLibrary;               // layer 2, table model (throws if no store)
  get attachments(): AttachmentManager;      // layer 2, column model (always available)
  get uploads(): ResumableUploadManager;     // resumable proxy (throws if no uploadSessions)
  get directUploads(): DirectUploadManager;  // direct presigned multipart (throws if no direct)
}
```

`media.attachments` is the [attachment column model](/docs/concepts/attachments) and is always provided — it only needs storage (and an [image processor](/docs/packages/image-sharp) for variants), no store or table. `media.library` is the [media table](/docs/concepts/two-layers#layer-2--media-library) and throws until you pass a `store`.

```ts
@Injectable()
export class Files {
  constructor(private readonly media: MediaService) {}
  save = (p: string, b: Buffer) => this.media.disk('s3').put(p, b);
}
```

## tus controller

When `tus` is configured, `MediaUploadController` is mounted at `media/uploads`, implementing the tus protocol over the [resumable engine](/docs/concepts/uploads). Remember the raw-body parser:

```ts
app.use('/media/uploads', express.raw({ type: 'application/offset+octet-stream' }));
```

## Protecting the routes

The upload controllers (`MediaUploadController` for tus, `MediaMultipartUploadController`, `MediaDirectUploadController`) carry **no auth of their own: uploads are unauthenticated until you protect them.** In order of preference:

1. **Mount them yourself** with the official tools (recommended).
2. **`decorators`** on the routes this module mounts.
3. **`guards`**, kept for compatibility.

Every upload controller is marked `@Can.Anyone()`-open (it defines `'authorization:can-anyone'` metadata, with no dependency on `@nestjs/authorization`), so the official deny-by-default global `AuthorizationGuard` doesn't refuse it. That mark only opens a route that declares no requirement: a `@Can(...)` you add, by any of the three ways below, is still checked (401 for a guest, 403 for a user the policy denies).

### 1. Mount it yourself (recommended)

This is how NestJS's first-party packages work: they give you the service, you write the controller, and you protect it like any other route of yours. `mount: false` mounts **no** upload controller, while every provider keeps working (`MediaService`, and the `MEDIA_TUS` / `MEDIA_UPLOADS` / `MEDIA_DIRECT` handlers). You then serve the same routes by extending the exported controller classes, at a path you pick, with ordinary Nest decorators:

```ts
import { Can } from '@nestjs/authorization';
import { Controller } from '@nestjs/common';
import {
  MediaDirectUploadController,
  MediaModule,
  MediaMultipartUploadController,
  MediaUploadController,
} from '@dudousxd/nestjs-media';

@Can(MediaPolicy, 'upload')
@Controller('api/uploads')
export class UploadsController extends MediaUploadController {} // tus

@Can(MediaPolicy, 'upload')
@Controller('api/uploads')
export class UploadPartsController extends MediaMultipartUploadController {} // parallel parts

@Can(MediaPolicy, 'upload')
@Controller('api/uploads/direct')
export class DirectUploadsController extends MediaDirectUploadController {} // S3 presign

@Module({
  imports: [
    AuthorizationModule.forRoot(),
    MediaModule.forRoot({
      // …
      tus: { disk: 'local', basePath: '/api/uploads' }, // the tus Location header points here
      mount: false,
    }),
  ],
  controllers: [UploadsController, UploadPartsController, DirectUploadsController],
  providers: [MediaPolicy],
})
export class AppModule {}
```

Mount only the ones you use, and put the raw-body parser on your path (`app.use('/api/uploads', express.raw(...))`). The subclasses inherit every route, parameter and the constructor's injection, so they need no constructor of their own; anything you add (`@UseGuards(AuthenticationGuard)`, a per-method `@Can`, an interceptor) is plain Nest. For full control, skip the classes and inject the handlers into a controller of your own: `@Inject(MEDIA_TUS) tus: TusUploadHandler` (`tus.handle({ method, uploadId, headers, body })` returns the status, headers and body to send), `MediaService.uploads` and `MediaService.directUploads`. `mount` works the same on `forRootAsync` (a static field, see below).

### 2. `decorators`

To keep the routes this module mounts (`media/uploads`, `media/uploads/direct`), pass `decorators`: class decorators applied to **every** upload controller the module mounts. Default: none.

```ts
import { AuthenticationGuard } from '@nestjs/authentication';
import { Can } from '@nestjs/authorization';
import { UseGuards } from '@nestjs/common';

MediaModule.forRoot({
  // …
  decorators: [UseGuards(AuthenticationGuard), Can(MediaPolicy, 'upload')],
});
```

On `forRootAsync` it is a static field on the config object, like `guards` and `mount`, since it shapes the routes before any factory runs. Each registration decorates a fresh subclass of each controller, so one registration's decorators never leak into another. With `decorators` set, resolve the controllers by route, not with `app.get(MediaUploadController)`.

### 3. `guards` (compatibility)

`guards` gates the mounted controllers with guard classes. A plain array gates all three uniformly; a per-surface object gates each independently, since the surfaces often carry different sensitivity (session creation admin-only, part PUTs any authenticated user):

```ts
MediaModule.forRoot({
  // …
  guards: { tus: [AdminGuard], multipart: [AuthenticatedGuard] }, // direct omitted → unguarded
});
```

An omitted key (or the whole option) leaves that surface unguarded. On `forRootAsync`, `guards` is a *static* field on the config object, not resolved via `useFactory`, since controllers are wired at module-build time; a guard that needs async-resolved config (e.g. a `ConfigService` secret) should inject it itself via DI, with its providing module passed through `imports`. `guards` composes with `decorators` (both must pass; `guards` runs first). The guards are stamped on the shared controller classes, so subclasses you mount yourself inherit them too.

## Mounting only what you use

`forRoot` mounts a controller only when its feature is configured (`tus` → tus, `uploadSessions` → multipart, `direct` → direct). `forRootAsync` can't know that in time, so it mounts all three by default and each one 501s if you never configure its feature in the factory. Either way, `mount` turns surfaces off, so they 404 instead of existing as dead surface:

```ts
MediaModule.forRootAsync({
  useFactory: () => ({ /* … */ }),
  mount: { direct: false }, // no direct-upload config → don't mount the controller at all
});
```

`mount: false` turns them all off (see [Mount it yourself](#1-mount-it-yourself-recommended)).

## Direct upload controller

When `direct` is configured (with a presign/multipart-capable disk like S3), `MediaDirectUploadController` is mounted at `media/uploads/direct`, orchestrating browser-to-S3 [presigned multipart uploads](/docs/concepts/uploads#direct-presigned-multipart-server) over `DirectUploadManager` (`media.directUploads`). It exposes `initiate` / per-part presign / `complete` / `abort` — no raw-body parser is needed, since the bytes go straight to S3.

```ts
direct: { disk: 's3', partSize: 8 * 1024 * 1024 } // partSize optional, default 8 MiB
```

## The `/storage` subpath

For consumers that want only the filesystem facade, without the media-library layer:

```ts
import { StorageManager, type StorageDriver } from '@dudousxd/nestjs-media/storage';
```

## Injection tokens

```ts
import {
  MEDIA_STORAGE, MEDIA_LIBRARY, MEDIA_ATTACHMENTS, MEDIA_UPLOADS, MEDIA_TUS, MEDIA_DIRECT,
} from '@dudousxd/nestjs-media';
```

<Callout type="info">
Inject `MediaService` for normal use; reach for the tokens only when you need the raw `StorageManager`/`MediaLibrary`/`ResumableUploadManager`/`DirectUploadManager` (e.g. wiring a custom controller).
</Callout>

## Facade re-exports

`@dudousxd/nestjs-media`'s entrypoint also re-exports the error classes (`FileNotFoundError`, etc.), `ResumableUploadManager`, `mediaDiagnosticKey`, `MediaDiagnosticEvent`, `publishMedia`, and the storage-consumer/upload-session types (`StatResult`, `TemporaryUrlOptions`, `ListResult`, `ListEntry`, `ListOptions`, `MultipartPart`, `UploadSession`, `UploadSessionStore`, `UploadSessionListFilter`, `CreateUploadInput`) from `@dudousxd/nestjs-media-core` — so a consumer app doesn't need its own dependency on `-core` just to reach these:

```ts
import {
  FileNotFoundError, ResumableUploadManager, mediaDiagnosticKey, publishMedia,
  type MediaDiagnosticEvent, type UploadSession, type UploadSessionStore,
} from '@dudousxd/nestjs-media';
```

## Peer dependencies

`@nestjs/common` and `@nestjs/core` (v10, v11 or v12), `reflect-metadata`, and `@dudousxd/nestjs-media-core`. Disks, stores, and the image engine are separate installs.
