`@dudousxd/nestjs-media-core` is the core every other package builds on. Its engines take the disks of [`@nestjs/storage`](https://docs.nestjs.com/application/file-storage) (a type-only dependency: core never loads it at runtime), so they work with a `Storage` from `StorageModule`, or with disks you build by hand. The [umbrella package](/docs/packages/nestjs) adds DI wiring.

## What's inside

**The disks it takes** — `Storage` from `@nestjs/storage` as it is, or anything shaped like it:

```ts
interface MediaDisks {
  readonly defaultDisk: string;
  disk(name?: string): StorageDisk;
  names(): string[];
}
```

**The SPIs** — the contracts stores, image engines and multipart side-cars implement:

```ts
interface MediaStore { save/find/listByOwner/delete/nextOrder (+ count/aggregate/list for the dashboard) }
interface ImageProcessor { convert(input, preset): Promise<ConversionResult> }
interface MultipartUploadDriver {   // native multipart for one disk (see -disk-s3)
  createMultipartUpload / uploadPart / presignUploadPart / completeMultipartUpload / abortMultipartUpload
  listFolders?(prefix, { cursor, limit }): Promise<FolderListing>
}
```

**`MediaLibrary`** — the *table* orchestrator: `attach / list / delete / url / locate / ensureConversion`, the `for(ownerType, id)` owner binding, collections, MIME validation, conversion generation, and diagnostics.

**`Attachment` + `AttachmentManager`** — the *column* model ([attachments](/docs/concepts/attachments)): `createFromFile`, `url`, `signedUrl`, `delete`.

**The upload engine** — `ResumableUploadManager`, `DirectUploadManager` and the framework-agnostic `TusUploadHandler`.

**Disk helpers** — what `@nestjs/storage` doesn't cover, used by the dashboard and telescope:

| Export | What it does |
| --- | --- |
| `diskCapabilities(disk, sidecar?)` | `{ presign, multipart, publicUrls, list, ranged }` |
| `listFolderLevel(disk, prefix, page, sidecar?)`, `foldListing(disk, prefix, page)` | one folder level ([Folders](/docs/concepts/folders)) |
| `folderListingLimit(limit)`, `DEFAULT_FOLDER_LISTING_LIMIT`, `MAX_FOLDER_LISTING_LIMIT` | the page size of a folder listing: `limit`, else 50, at most 1000; `RangeError` unless a positive integer |
| `keySegment(text)`, `assertMediaKey(key)`, `folderPrefix(prefix)` | `@nestjs/storage`'s key rule, for keys built from user input |
| `fileUrl(disk, key, options?)` | the public URL, else a signed one |
| `multipartFor(drivers, disk)` | the side-car configured for a disk |

**`resolveUploadMode`** — the `auto | proxy | direct` decision from a disk's capabilities.

**Diagnostics** — `publishMedia` + the `aviary:media:*` events.

**Errors** — `MediaNotFoundError`, `MimeNotAllowedError`, `ConversionNotDefinedError`, `ImageProcessorMissingError`, `UploadSessionNotFoundError`, `UploadOffsetConflictError`, `InvalidPartNumberError`, `UnsupportedOperationError`, `InvalidMediaKeyError` (status 400), `InvalidListingCursorError` (a forged folder-listing `cursor`, status 400), each with a stable `code`. Storage errors are `@nestjs/storage`'s.

## Using it directly

You rarely import core in app code — you use the [umbrella module](/docs/packages/nestjs). For non-Nest hosts or custom wiring:

```ts
import { InMemoryDisk, Storage } from '@nestjs/storage';
import { MediaLibrary } from '@dudousxd/nestjs-media-core';

const storage = new Storage(new Map([['local', new InMemoryDisk()]]), 'local');
const library = new MediaLibrary({ storage, store, collections, imageProcessor });
await library.attach({ ownerType: 'Post', ownerId: '1', collection: 'gallery', fileName, mimeType, contents });
```

See [Concepts → The two layers](/docs/concepts/two-layers) for the media-library API.
